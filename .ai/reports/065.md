## What each action writes (all through `api/firebase_proxy.php` via `firebaseFetch`, CSRF as before)
- **تفعيل** (users row, not subscribed): modal (name prefilled, plan شهري/سنوي) → `activateDevice()`, which is the old key logic from `generateAndSaveKey` moved into one function (the generator tab now calls it too).
  - PUT `licenses/{cleanKey}`: key, displayKey, deviceCode (dashed), subscriberName, plan, activatedAt, expiresAt, isRevoked=false, lastCheckedAt.
  - PUT `devices/MSRB-XXXX-XXXX`: the same payload.
  - A request id (requests flow only) also writes `subscription_requests/{id}/status` = COMPLETED and `.../activationKey`.
  - The device code is rebuilt in dashed form from a cleaned key. An invalid code or plan is rejected before any write. A failed write on either node shows an error.
  - After success: toast, local lists updated, and WhatsApp opens with the existing message text (now `activationMessage()`, shared with the generator's button) if the user has a phone. If the popup is blocked, a toast button «إرسال واتساب» is shown.
- **تمديد** (subscribed row): modal (plan) → PATCH `{expiresAt, plan, lastCheckedAt}` on `licenses/{key}` and on `devices/{code}`. `expiresAt` = max(now, current expiresAt) + 30/365 days. The key comes from the newest license for that device (`subscriptionByDevice[...].key`, now stored by `rememberSubscription`). If the key is unknown, only `devices/{code}` is written.
- **إلغاء التفعيل** (subscribed row): confirm dialog → PATCH `{isRevoked:true, lastCheckedAt}` on both nodes.
- The users table, status counters and KPI/expiring panels are redrawn locally (`applyLocalSubscription`, `renderUsersTable`, `updateStats`, `refreshTask036Panels`) with no full reload.
- **Requests row**: «تفعيل وإرسال واتساب» (when the requester has a phone) = `activateDevice` with the request id, then WhatsApp opens to their number with key and plan. A secondary «تفعيل فقط» keeps the old behaviour (generator tab). Without a phone, only the plain «تفعيل» is shown.

No new Firebase paths (licenses, devices, subscription_requests are already in the proxy allowlist; PATCH is already allowed there). No secrets in JS.
