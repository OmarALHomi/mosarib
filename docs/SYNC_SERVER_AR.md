# قناة المزامنة الخاصة (ح٢٢) — دليل المالك

**الخلاصة في ثلاثة أسطر:** التطبيق يكلّم **خادمًا يملكه المالك** لا خدمة سحابية، عبر عقد مكتوب اسمه
`v1`. والخادم المرجعي الذي ينفّذه موجود في هذا المستودع (`server/baynana-sync-server.mjs`)،
**ويُختبر في CI** بمقارنة ردوده بما يفكّه التطبيق. و«نسخة قديمة تعمل بلا تعديل» ليست وعدًا هنا:
الحقول والمسارات مثبَّتة باختبار يسقط إن تغيّرت.

---

## ١. لماذا خادم خاص؟

| السبب | الأثر العملي |
|---|---|
| البيانات لا تُسلَّم لطرف ثالث | دفاتر العائلات تبقى على جهاز المالك أو خادمه |
| لا تكلفة شهرية مربوطة بحجم الاستخدام | خادم واحد صغير يخدم عائلات كثيرة |
| لا سياسات متغيّرة من مزوّد خارجي | العقد عندنا، ولا يُغيّر تحت أقدام المستخدمين |
| الخروج ممكن | كل شيء موثّق هنا: يمكن نقل الخادم أو إيقافه بلا فقدان (ح٢٣) |

---

## ٢. العقد `v1` (وهو ما يفحصه CI)

المسار الأساسي واحد: `https://<الخادم>/api/v1/changes`.

### ٢.١ الإرسال (من الجهاز إلى الخادم)

```http
POST /api/v1/changes
Authorization: Bearer <رمز الجهاز>
Content-Type: application/json; charset=utf-8
```

```json
{
  "deviceId": "9f2c…",
  "items": [
    {
      "operationId": "op-…",
      "entityType": "entry",
      "entityId": "entry-…",
      "action": "UPSERT",
      "payload": "{\"id\":\"entry-…\",\"amountMinor\":\"1500000\",…}",
      "createdAt": 1767225596000
    }
  ]
}
```

والردّ **نتيجة لكل عنصر بنفس ترتيب الطلب**:

```json
{"outcomes":[
  {"operationId":"op-…","status":"ACCEPTED","retryable":false,"reason":""},
  {"operationId":"op-…","status":"REJECTED","retryable":false,"reason":"المبلغ «amountMinor» يجب أن يكون نصًّا بالوحدة الصغرى (ADR-04)، لا رقمًا"}
]}
```

### ٢.٢ السحب (من الخادم إلى الجهاز)

```http
GET /api/v1/changes?cursor=c:Mg&limit=50
Authorization: Bearer <رمز الجهاز>
```

```json
{"changes":[{"kind":"UPSERT","entityType":"entry","entityId":"entry-…","operationId":"op-…",
             "payload":"{…}","serverTime":1767225600000}],
 "nextCursor":"c:Mg","hasMore":true}
```

### ٢.٣ ثوابت العقد — ولكل ثابت عطلٌ يمنعه

| الثابت | العطل الذي يمنعه |
|---|---|
| **ترتيب الردّ = ترتيب الطلب** | نسبة نتيجة عنصر إلى عنصر آخر ⇒ «أُرسل» كاذبًا |
| **`operationId` مفتاح منع تكرار** | إعادة إرسال بعد انقطاع ⇒ قيد مزدوج ⇒ دَين مضاعف |
| **`serverTime` من الخادم بالمللي ثانية كعدد** | تغيير ساعة الهاتف يقلب ترتيب التغييرات |
| **المؤشر نصّ غير شفّاف يُنقل كما هو** | عميل يفترض أن المؤشر رقم ⇒ ينكسر عند أول تغيير للخادم |
| **`hasMore` صريح** | استنتاج النهاية من قلّة العناصر ⇒ فقدان تغييرات |
| **`retryable=false` يعني «لا تُعِد»** | إعادة أبدية تستهلك البطارية وتخفي سبب الرفض |
| **المبالغ نصّية بالوحدة الصغرى** | كسور عشرية على السلك ⇒ فرق فلس في دَين |

### ٢.٤ ماذا يفعل التطبيق بكل ردّ؟

| ردّ الخادم | ما يحدث في التطبيق |
|---|---|
| `200` + `ACCEPTED` | يُعلَّم العنصر مُرسلًا، ويُحدَّث مؤشر السحب |
| `200` + `REJECTED, retryable=true` | يبقى في الانتظار، ويُعاد بموعد أسّي (دقيقة ← ٦ ساعات) |
| `200` + `REJECTED, retryable=false` | «يحتاج تدخلًا» بسببه العربي، ولا يُعاد صامتًا، والبيانات تبقى |
| `401/403` | «رمز الجهاز مرفوض — راجع ضبط قناة المزامنة» (رفض دائم، لا إعادة أبدية) |
| `500..599` أو انقطاع | خطأ نقل مؤقّت: يُعاد لاحقًا، ولا يُلمس شيء في القاعدة |
| ردّ مشوّه أو ناقص | العنصر الذي لم يُقرأ ردّه **لا يُعلن نجاحه** |

## ٣. تشغيل الخادم المرجعي

```bash
# على الخادم (لا يحتاج أي اعتماد خارجي: Node وحده)
SYNC_TOKEN="$(openssl rand -base64 24)" \
STATE_FILE=/var/lib/baynana/sync-state.json \
TLS_CERT=/etc/letsencrypt/live/sync.example.com/fullchain.pem \
TLS_KEY=/etc/letsencrypt/live/sync.example.com/privkey.pem \
PORT=443 node server/baynana-sync-server.mjs
```

- **`SYNC_TOKEN`**: رمز الجهاز المشترك (يُضبط في إعداد الجهاز أيضًا). **إلزامي لأي نشر حقيقي**:
  بلا رمز لا مصادقة إطلاقًا، والخادم يطبع تنبيهًا صريحًا عندما يُشغَّل بلا رمز.
- **`STATE_FILE`**: ملفّ حالة صغير (JSON) يحفظ التغييرات بين التشغيلات. بدونه، الحالة في الذاكرة
  وتضيع بإعادة التشغيل (مناسب للتجربة فقط). خذ نسخة احتياطية منه كما تأخذ من قاعدة بيانات.
- **`TLS_CERT`/`TLS_KEY`**: التطبيق يرفض النصّ المكشوف (`usesCleartextTraffic="false"`)، فلا بدّ
  من شهادة TLS. (وإن شغّلت الخادم عبر وكيل عكسي مثل nginx، فاجعل الوكيل ينهي TLS.)
- **`PORT`**: المنفذ.

مثال وحدة `systemd` مختصرة:

```ini
[Unit]
Description=Baynana sync server
After=network.target

[Service]
Environment=PORT=8787
EnvironmentFile=/etc/baynana/sync.env      # SYNC_TOKEN و STATE_FILE
ExecStart=/usr/bin/node /opt/baynana/server/baynana-sync-server.mjs
Restart=always
User=baynana

[Install]
WantedBy=multi-user.target
```

## ٤. ضبط التطبيق على الخادم

1. **العنوان**: في `app/src/main/assets/sync_endpoint.txt` ضع سطرًا واحدًا:
   `https://sync.example.com` (بلا مسار؛ يُضاف `/api/v1/changes` تلقائيًّا).
   > **لماذا في الأصل البنائي لا في إعداد؟** لأن تغيير العنوان يعني إرسال دفاتر العائلة إلى خادم
   > آخر. لو صار قابلًا للتحرير من الشاشة لكفى من يمسك الجهاز دقيقةً ليحوّل البيانات إلى خادمه.
   > فالتغيير يحتاج **بناءً جديدًا** — وهو نفس قرار قناة التحديث (ح٢٠).
2. **رمز الجهاز**: يُخزَّن على الجهاز في `baynana_sync_prefs/sync_device_token`، ولا يُطبع ولا
   يُعرض ولا يُسجَّل في أي رسالة خطأ.
   > **الحلقة المفتوحة المعلنة صراحةً:** لا توجد بعد شاشة تُدخل الرمز على الجهاز (تسجيل جهاز
   > بخطوة واحدة). حتى تُضاف، القناة تبقى **مغلقة** بحكم `SyncConfig.isConfigured`، والتطبيق يعمل
   > محليًّا كما كان. وهذا مقصود: قناة تُفتَح بلا رمز تُرسل دفاتر العائلة بلا مصادقة.
3. **البناء والتثبيت**: بناء إصدار عادي (ح٢١). ولا حاجة لأي تعديل في التطبيق نفسه عند نقل الخادم:
   يكفي بناء بعنوان جديد.

## ٤.١ نقل دفتر قديم إلى هذا الخادم (أوامر الترحيل)

الاستيراد يمرّ من عقد المزامنة نفسه (لا مسار كتابة خاص)، وله ثلاثة أوامر في `tools/migrate.mjs`.
وهي تُشغَّل من حاسوب المالك، ولا تحتاج واجهة:

```bash
# ١) تصدير جرد من أي مصدر يُقرأ بـJSONL
node tools/migrate.mjs --export /tmp/ledger.jsonl

# ٢) استيراد الملفّ إلى الخادم عبر العقد (ثم مقارنة الجرد فورًا)
node tools/migrate.mjs --import /tmp/ledger.jsonl --url https://sync.example.com --token <رمز الجهاز>

# ٣) لاحقًا، وأي وقت: هل وصل كل شيء؟
node tools/migrate.mjs --verify /tmp/ledger.jsonl --url https://sync.example.com --token <رمز الجهاز>
```

والنتيجة إمّا «✅ صفر فرق في الجرد» أو **قائمة فروق بالعربية** ورمز خروج `1` (فتصلح للتشغيل الآلي).

ثلاث نقاط مهمّة لمن يُشغّل الخادم:

- **الملفّ يُفحص على نفسه أيضًا**: تُقارَن أرقام ترويسته بأحداثه، فملفّ مُعدَّل أو مبتور يُوسم
  «غير متّسق مع ترويسته» ولا يُقبل نقله — ولو طابق ما في الخادم.
- **إعادة الاستيراد آمنة**: منع التكرار بالمُعرّف في العقد، فلا تُضاعف قيدًا بإعادة الأمر.
- **الخادم لا يمسح شيئًا**: الاستيراد يضيف أحداثًا، والفشل أولى من المسح دائمًا.

التفاصيل الكاملة للمالك في `docs/MIGRATION_AR.md`.

## ٤.٢ قناة الإصدار على الخادم نفسه (عنوان واحد، عقدان)

الخادم المرجعي ينفّذ العقد الثاني كذلك: **`GET /api/v1/app-release`** — ملفّ الإصدار الموقّع كما هو.

```bash
RELEASE_FILE=/srv/baynana/app-release.txt \
SYNC_TOKEN=... STATE_FILE=/srv/baynana/state.json TLS_CERT=... TLS_KEY=... \
node server/baynana-sync-server.mjs
```

ثلاث خصائص مقصودة، وكلّها في مقابل عقد المزامنة:

1. **عامّ بلا رمز**: الملفّ موقّع بمفتاح المالك، وقراءته لا تكشف شيئًا، وفحص التحديث يجب أن يعمل على
   جهاز جديد لم يُضبط له رمز مزامنة بعد. (مسار المزامنة يبقى برمز إلزامي.)
2. **النصّ يُخدَم كما هو**: لا إعادة ترميز JSON، لأن التوقيع يُتحقَّق من البايتات، والتحقق يقع في
   التطبيق لا في الخادم.
3. **بلا `RELEASE_FILE` ⇒ `404` عربية** صريحة («لا ملفّ إصدار مُهيّأ على هذا الخادم») — لا صفحة HTML
   ولا نجاح كاذب. وبهذا يستطيع المالك أن يترك قناة الإصدار على GitHub Pages، أو يجمعها مع المزامنة
   على عنوان واحد: القرار قراره، والتطبيق لا يعرف الفرق لأنه يتكلّم العقد نفسه.

وإن جمعتهما على عنوان واحد، صار سطر واحد في `release_endpoint.txt` هو العنوان المشترك.

## ٥. ما لا يفعله هذا الخادم (مُعلن لا منسي)

| النقص | الأثر | أين يُعالَج |
|---|---|---|
| مصادقة على مستوى الغرفة (تفويض دقيق) | رمز واحد للأجهزة يعني أن أي جهاز يعرف الرمز يشارك الدلتا | ح٢٣ (مع الترحيل) وح١٦ للأدمن |
| دمج تعارضات على الخادم | الدمج يقوم عند العميل بقواعد الغرفة (الأقدم أولًا، والحجر يمنع الإنعاش) | ح٦ مُنفَّذ ويعمل |
| تشفير طرف لطرف | الخادم يرى الحمولة كما هي | قرار لاحق يُعلن قبل وعده للناس |
| واجهة إدارة للخادم | لا صفحات ولا لوحة: المسارات الأربعة فقط | لوحة الأدمن (ح١٦) |

**وضع هذا الملفّ في المستودع: مرجعُ عقدٍ واختبار، لا خادم إنتاج.** أي نشر حقيقي عليه أن يلتزم
بما في الجدول أعلاه، ويُعلن ما ينقصه بصراحة.

## ٦. الفحص المستمر في CI

```bash
node tools/sync_contract_test.mjs --check     # سقوط إن تغيّر شكل الردّ أو مُنع شيء
node tools/sync_contract_test.mjs --write     # إعادة توليد المتجهات بعد تغيير مقصود في العقد
```

الأداة تُشغّل الخادم المرجعي داخل العملية، وتتحقق من: منع التكرار، ورفض المبلغ الرقمي، وترتيب
النتائج، وعمل المؤشر، و`hasMore`، و`401` بلا رمز، و`404` لمسار غير معروف. ثم تُثبّت الردود
الحقيقية في `app/src/test/java/com/baynana/domain/sync/SyncWireVectors.kt`، ويقرؤها اختبار
Kotlin على تنفيذ `org.json` الحقيقي في أندرويد. فالمتجهات **ليست وصفًا للعقد بل ردّ الخادم**.

وعلى السلك فعلًا: `HttpSyncTransportTest` يفتح خادمًا محليًّا داخل الاختبار ويثبت أن
`Authorization: Bearer …` يصل في الرأس (لأن JDK يخفي هذا الرأس عن `getRequestProperty`، فالالتقاط
وحده لا يُثبت شيئًا).

## ٧. قائمة تحقّق قبل النشر

- [ ] `SYNC_TOKEN` مضبوط وقوي، والرمز محفوظ بعيدًا عن المستودع.
- [ ] TLS يعمل، والنصّ المكشوف مُغلق (`usesCleartextTraffic="false"` في المانيفست).
- [ ] `STATE_FILE` على قرص دائم + نسخة احتياطية دورية.
- [ ] `sync_endpoint.txt` يحمل عنوان الخادم الجديد (ببناء جديد)، و`SyncConfig` يرفض ما ليس https.
- [ ] الرمز مُدخل على كل جهاز (الحلقة المفتوحة أعلاه) — وإلا فالقناة مغلقة والتطبيق محلي.
- [ ] `node tools/sync_contract_test.mjs --check` يمرّ محليًّا وعلى CI.
- [ ] اختبار حقيقي على جهازين: قيد يُكتب على الأول ⇒ يظهر على الثاني، وإعادة الإرسال لا تُضاعف.
- [ ] إن نُقل دفتر قديم: `--verify` قال «صفر فرق»، والنسخة الاحتياطية للخادم القديم محفوظة.
- [ ] إن كانت قناة الإصدار على الخادم نفسه: `curl -s .../api/v1/app-release` يردّ نصّ الملفّ الموقّع
      (لا صفحة HTML، ولا رمز مزامنة مطلوبًا).
